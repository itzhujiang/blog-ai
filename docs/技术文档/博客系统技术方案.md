# 个人博客系统技术方案文档

## 1. 项目概述

### 1.1 项目背景

本项目旨在创建一个个人成长分享博客，集生活故事分享、技术学习记录、AI作品展示于一体。这是一个内容为主的个人博客系统，强调阅读体验和SEO优化。

### 1.2 核心功能

- **文章系统**：文章列表、详情页、分类浏览、搜索功能
- **评论系统**：支持嵌套回复、访客评论、评论审核
- **分类系统**：多分类支持（技术学习、生活故事、AI创作）
- **搜索功能**：全文搜索文章标题和摘要
- **关于我页面**：个人简介、联系方式、社交媒体链接

### 1.3 技术目标

- **性能目标**：
  - 首屏加载时间 < 3秒
  - 文章详情页加载时间 < 2秒
  - 支持 ISR 缓存，减少服务器压力

- **可维护性目标**：
  - 使用团队熟悉的技术栈（Sequelize）
  - 清晰的代码结构和模块划分
  - 完善的类型定义（TypeScript）

- **扩展性目标**：
  - 支持未来功能扩展（AI作品展示）
  - 灵活的内容格式（MDX）
  - 可扩展的数据库设计

- **SEO 目标**：
  - 所有页面服务端渲染
  - 友好的 URL 结构
  - 完善的 meta 标签

### 1.4 部署环境

- **服务器**：阿里云 ECS（2核2G，99元/年）
- **并发量**：低（个人博客）
- **CDN**：暂不使用

## 2. 技术栈选型

### 2.1 前端技术栈

#### 2.1.1 框架选择

- **选择**：React 19.2.0
- **理由**：
  - Next.js 16 基于 React 19
  - 团队熟悉 React 生态
  - 强大的组件化能力
- **权衡考虑**：
  - 优势：生态成熟、社区活跃、学习资源丰富
  - 劣势：包体积相对较大
  - 替代方案：Vue、Svelte

#### 2.1.2 元框架选择

- **选择**：Next.js 16.0.1 (App Router)
- **理由**：
  - 原生支持 SSR/SSG/ISR 多种渲染策略
  - 优秀的 SEO 支持
  - 内置图片优化（next/image）
  - 强大的文件系统路由
- **权衡考虑**：
  - 优势：开发体验好、性能优秀、部署简单
  - 劣势：学习曲线（App Router 较新）
  - 替代方案：Nuxt（Vue）、SvelteKit（Svelte）

#### 2.1.3 样式方案

- **选择**：Tailwind CSS v4
- **理由**：
  - 快速开发，无需编写 CSS
  - 响应式设计简单
  - 暗色模式支持
  - 与 Next.js 深度集成
- **权衡考虑**：
  - 优势：开发效率高、一致性好、可维护性强
  - 劣势：HTML 类名较长
  - 替代方案：CSS Modules、Styled Components

#### 2.1.4 内容格式

- **选择**：MDX（Markdown + JSX）
- **理由**：
  - 支持在 Markdown 中使用 React 组件
  - 灵活处理图片优化（next/image）
  - 代码语法高亮
  - 可扩展性强（自定义组件）
- **权衡考虑**：
  - 优势：灵活、强大、与 Next.js 集成好
  - 劣势：需要运行时解析（但 ISR 缓存后影响小）
  - 替代方案：纯 Markdown + 预编译

### 2.2 后端技术栈

#### 2.2.1 API 架构

- **选择**：Next.js API Routes (REST API)
- **理由**：
  - 与前端代码在同一项目中，部署简单
  - 支持 Server Actions（表单处理）
  - 无需额外的后端服务
- **权衡考虑**：
  - 优势：开发简单、部署方便、类型共享
  - 劣势：不适合复杂的后端逻辑
  - 替代方案：独立的 Node.js 后端、GraphQL

#### 2.2.2 日志方案

- **选择**：log4js
- **理由**：
  - 成熟稳定的 Node.js 日志库
  - 支持多种日志输出方式（文件、控制台、远程服务）
  - 灵活的日志级别配置（trace、debug、info、warn、error、fatal）
  - 支持日志文件轮转（按大小、按日期）
  - 与 Next.js API Routes 兼容良好
- **权衡考虑**：
  - 优势：功能完整、配置灵活、社区活跃
  - 劣势：需要手动配置，不如 pino 性能高
  - 替代方案：pino（性能更好）、winston（功能更丰富）

- **配置方案**：
  ```typescript
  // utils/logger.ts
  import log4js from 'log4js';

  log4js.configure({
    appenders: {
      console: { type: 'console' },
      file: {
        type: 'dateFile',
        filename: 'logs/app.log',
        pattern: 'yyyy-MM-dd',
        keepFileExt: true,
        numBackups: 7,  // 保留7天日志
      },
      error: {
        type: 'dateFile',
        filename: 'logs/error.log',
        pattern: 'yyyy-MM-dd',
        keepFileExt: true,
        numBackups: 30,  // 错误日志保留30天
      },
    },
    categories: {
      default: { appenders: ['console', 'file'], level: 'info' },
      error: { appenders: ['console', 'error'], level: 'error' },
      database: { appenders: ['console', 'file'], level: 'debug' },
      api: { appenders: ['console', 'file'], level: 'info' },
    },
  });

  export const logger = log4js.getLogger();
  export const errorLogger = log4js.getLogger('error');
  export const dbLogger = log4js.getLogger('database');
  export const apiLogger = log4js.getLogger('api');
  ```

- **使用场景**：
  - **API 请求日志**：记录请求路径、方法、响应时间
  - **数据库操作日志**：记录查询语句、执行时间
  - **错误日志**：记录异常堆栈、错误上下文
  - **业务日志**：记录关键业务操作（发布文章、评论审核等）

- **日志目录结构**：
  ```
  logs/
  ├── app.log              # 当天应用日志
  ├── app.2026-02-02.log   # 历史应用日志
  ├── error.log            # 当天错误日志
  └── error.2026-02-02.log # 历史错误日志
  ```

#### 2.2.3 服务端渲染策略

- **选择**：混合渲染策略
- **应用场景**：
  - **ISR（文章列表、文章详情）**：
    - revalidate: 3600 秒（1小时）
    - 配合 On-Demand Revalidation（发布/更新时触发）
    - 理由：内容更新频率低（每周2-3篇），ISR 可以大幅减少服务器压力

  - **CSR（统计信息、评论区）**：
    - 阅读量、评论数实时获取
    - 评论列表客户端加载
    - 理由：这些数据频繁变化，不影响 SEO

  - **SSG（关于我页面）**：
    - 构建时生成
    - 理由：内容几乎不变

- **理由**：
  - 发布频率低（每周2-3篇），不需要频繁重新生成
  - ISR 配合 On-Demand 可以精确控制更新时机
  - 服务器配置有限（2核2G），ISR 可以减少压力
  - 静态内容和动态数据分离，提升性能

### 2.3 数据库和存储

#### 2.3.1 数据库选择

- **选择**：PostgreSQL 14+
- **理由**：
  - 强大的全文搜索功能（支持中文）
  - 优秀的递归查询支持（评论嵌套回复）
  - JSON 字段支持（关于我页面的灵活数据）
  - 成熟稳定，性能优秀
- **权衡考虑**：
  - 优势：功能强大、性能好、社区活跃
  - 劣势：相比 MySQL 稍复杂
  - 替代方案：MySQL（但全文搜索和递归查询支持较弱）

#### 2.3.2 ORM/查询工具

- **选择**：Sequelize
- **理由**：
  - **团队熟悉**（最重要的理由）
  - 成熟稳定，社区庞大
  - 支持 PostgreSQL 的高级特性
  - 灵活的查询 API
- **权衡考虑**：
  - 优势：团队熟悉、灵活、功能完整
  - 劣势：TypeScript 支持需要手动配置、类型推断不如 Prisma
  - 替代方案：Prisma（类型安全更好，但团队不熟悉）

#### 2.3.3 文件存储方案

- **选择**：本地文件系统
- **存储结构**：
  ```
  /content/articles/     # Markdown 文件
  /public/images/        # 图片资源
  ```
- **理由**：
  - 简单直接，无需额外服务
  - 成本低（使用服务器存储）
  - 便于备份和迁移
- **权衡考虑**：
  - 优势：简单、成本低、易于管理
  - 劣势：扩展性有限（未来可迁移到 OSS）
  - 替代方案：阿里云 OSS、AWS S3

### 2.4 性能和优化

#### 2.4.1 图片优化

- **方案**：Next.js Image 组件 + 自动格式转换
- **实施细节**：
  ```tsx
  <Image
    src="/images/article.jpg"
    alt="文章配图"
    width={800}
    height={600}
    loading="lazy"
    placeholder="blur"
  />
  ```
- **优势**：
  - 自动转换为 WebP/AVIF 格式
  - 响应式图片（不同尺寸）
  - 懒加载
  - 占位符（提升用户体验）

#### 2.4.2 缓存策略

- **ISR 缓存**：
  - 文章列表：1小时
  - 文章详情：1小时
  - 配合 On-Demand Revalidation

- **浏览器缓存**：
  - 静态资源：长期缓存（1年）
  - HTML：短期缓存（1小时）

- **数据库连接池**：
  ```typescript
  pool: {
    max: 3,        // 最大连接数（2G内存限制）
    min: 0,
    idle: 10000,
    acquire: 30000,
  }
  ```

#### 2.4.3 CDN 使用

- **选择**：暂不使用
- **理由**：
  - 个人博客，访问量不高
  - 成本考虑
  - ISR 已经提供了足够的性能优化
- **未来考虑**：
  - 如果访问量增长，可以考虑使用阿里云 CDN
  - 或者迁移到 Vercel（自带全球 CDN）

### 3.3 数据流设计

#### 文章列表页数据流

```
1. 用户访问 /articles
2. Next.js 检查 ISR 缓存
   - 如果缓存有效（< 1小时）：直接返回缓存的 HTML
   - 如果缓存过期：后台触发重新生成
3. 重新生成流程：
   - Sequelize 查询数据库（articles 表）
   - 获取文章元数据（title, slug, excerpt, thumbnail_url）
   - 渲染 React 组件
   - 生成 HTML 并缓存
4. 返回 HTML 给用户
5. 客户端 hydration
6. CSR 获取统计信息（阅读量、评论数）
```

#### 文章详情页数据流

```
1. 用户访问 /articles/[slug]
2. Next.js 检查 ISR 缓存
3. 重新生成流程：
   - Sequelize 查询数据库（获取文章元数据）
   - 读取文件系统（Markdown 文件）
   - MDX 解析 Markdown 为 HTML
   - 渲染 React 组件
   - 生成 HTML 并缓存
4. 返回 HTML 给用户
5. 客户端 hydration
6. CSR 获取统计信息和评论列表
```

#### 发布文章流程

```
1. 后台管理系统提交文章
2. 保存到数据库（元数据）
3. 保存到文件系统（Markdown 内容）
4. 调用 On-Demand Revalidation API
5. Next.js 清除相关页面缓存
6. 下次访问时重新生成
```

## 4. 关键技术决策

### 4.1 决策一：选择 Sequelize 而非 Prisma

- **问题**：选择哪个 ORM 工具？
- **方案**：Sequelize
- **理由**：
  - 团队熟悉 Sequelize，可以加快开发速度
  - 减少学习成本和技术风险
  - Sequelize 功能完整，满足项目需求
- **影响**：
  - 需要手动配置 TypeScript 类型
  - 类型推断不如 Prisma 自动化
  - 但开发效率更高（团队熟悉）

### 4.2 决策二：文章列表和详情页都使用 ISR

- **问题**：如何平衡性能和内容实时性？
- **方案**：ISR (revalidate: 3600) + On-Demand Revalidation
- **理由**：
  - 发布频率低（每周2-3篇），不需要频繁重新生成
  - ISR 可以大幅减少服务器压力（2核2G配置有限）
  - On-Demand Revalidation 可以精确控制更新时机
  - 用户可以接受一定延迟
- **影响**：
  - 性能优秀（大部分请求返回缓存）
  - 服务器压力小
  - 需要实现 On-Demand Revalidation API

### 4.3 决策三：统计信息使用 CSR 实时获取

- **问题**：阅读量、评论数如何展示？
- **方案**：客户端 CSR 实时获取
- **理由**：
  - 这些数据频繁变化
  - 不影响 SEO（搜索引擎不关心阅读量）
  - 可以实现实时更新
  - 与 ISR 缓存的静态内容分离
- **影响**：
  - 首屏不显示统计信息（需要加载）
  - 需要额外的 API 请求
  - 但用户体验更好（实时数据）

### 4.4 决策四：使用 MDX 而非预编译 HTML

- **问题**：Markdown 何时解析为 HTML？
- **方案**：运行时解析（MDX）
- **理由**：
  - 文章包含图片和代码，需要动态处理
  - MDX 支持 React 组件（next/image、代码高亮）
  - ISR 缓存后，解析开销可以忽略
  - 灵活性更好，易于扩展
- **影响**：
  - 每次 ISR 重新生成时需要解析 Markdown（~15-25ms）
  - 但用户看到的是缓存的 HTML，速度很快
  - 可以使用自定义组件（提示框、警告框等）

### 4.5 决策五：数据库连接使用单例模式

- **问题**：如何管理 Sequelize 数据库连接？
- **方案**：单例模式 + 连接池
- **理由**：
  - 避免重复创建连接的开销
  - 连接池自动管理连接
  - 适合 Next.js 的服务端环境
  - 使用 global 对象处理热重载
- **影响**：
  - 性能更好
  - 资源利用率高
  - 需要正确配置连接池（max: 3，适应 2G 内存）

## 5. 风险和挑战

### 5.1 技术风险

#### 5.1.1 风险：服务器资源不足

- **影响**：2核2G 配置在高并发时可能不足
- **概率**：中（个人博客，并发量通常不高）
- **应对方案**：
  - ISR 策略减少服务器压力
  - 连接池限制为 3 个连接
  - 监控服务器资源使用情况
  - 必要时升级服务器配置

#### 5.1.2 风险：Sequelize TypeScript 类型问题

- **影响**：可能出现类型错误，影响开发体验
- **概率**：中
- **应对方案**：
  - 使用 `Model.init()` 方式定义模型
  - 手动定义接口和类型
  - 参考 Sequelize 官方 TypeScript 文档
  - 必要时使用 `sequelize-typescript` 装饰器

#### 5.1.3 风险：文件系统读取性能

- **影响**：大量文章时，文件读取可能成为瓶颈
- **概率**：低（ISR 缓存后影响小）
- **应对方案**：
  - ISR 缓存减少文件读取次数
  - 摘要存储在数据库，列表页不读文件
  - 监控文件读取性能
  - 必要时考虑预编译方案

### 5.2 性能挑战

#### 5.2.1 挑战：PostgreSQL 全文搜索性能

- **场景**：文章数量增长到 1000+ 篇时
- **解决方案**：
  - 创建全文搜索索引（GIN 索引）
  - 限制搜索结果数量（分页）
  - 只搜索标题和摘要（不搜索正文）
  - 监控搜索查询性能

#### 5.2.2 挑战：MDX 解析性能

- **场景**：文章很长（>5000字）时
- **解决方案**：
  - ISR 缓存后只解析一次
  - 监控解析时间
  - 必要时考虑预编译方案
  - 优化 MDX 插件配置

### 5.3 安全考虑

#### 5.3.1 XSS 防护

- **方案**：
  - React 自动转义输出
  - MDX 内容经过 sanitize 处理
  - 评论内容严格过滤
  - 使用 Content Security Policy (CSP)

#### 5.3.2 CSRF 防护

- **方案**：
  - Next.js API Routes 使用 CSRF token
  - 验证请求来源
  - 使用 SameSite Cookie

#### 5.3.3 SQL 注入防护

- **方案**：
  - Sequelize 参数化查询（自动防护）
  - 不使用原始 SQL（除非必要）
  - 输入验证和清理
