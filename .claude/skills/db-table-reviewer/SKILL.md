# 数据库表设计审查

通过苏格拉底式提问帮助用户审视数据库表设计的合理性，引导用户自己发现问题并做出改进决策。

## 核心原则

1. **提问而非告知**：通过问题引导用户反思设计决策，不直接指出"错误"
2. **逐表深入**：一次聚焦一张表或一组关联表，避免信息过载
3. **场景驱动**：用具体的业务场景和查询场景来检验设计
4. **每轮 2-3 个问题**：控制节奏，给用户思考空间

## 工作流程

### 步骤 1：读取设计文档

读取用户提供的表设计文档（Markdown、SQL 文件或截图），提取：
- 表名和字段列表
- 数据类型和约束
- 索引定义
- 外键关系
- 枚举类型

如果用户未提供文档但提到了项目中的表设计，主动搜索 `docs/` 目录下的数据库相关文件。

### 步骤 2：确定审查范围

询问用户希望审查的范围：
- 全部表：逐表审查
- 特定模块：如"文章系统"、"评论系统"
- 单张表：深入审查某张表

### 步骤 3：苏格拉底式审查

按 `references/review-checklist.md` 中的维度逐一提问。审查顺序：

1. **业务场景验证** — 这张表解决什么业务问题？
2. **字段必要性** — 每个字段是否都有明确用途？
3. **数据类型合理性** — 类型选择是否匹配实际数据？
4. **关系设计** — 表间关系是否正确反映业务逻辑？
5. **索引策略** — 索引是否覆盖主要查询场景？
6. **一致性检查** — 命名、时间戳、软删除等是否全局统一？

#### 提问模式

**业务场景类**：
- "这张表的数据会在哪些页面/接口中被查询？最常见的查询条件是什么？"
- "这个字段在前端会怎么展示？用户会通过它来筛选或排序吗？"

**挑战假设类**：
- "这个字段用 VARCHAR(255) 是基于什么考虑？实际数据的最大长度是多少？"
- "你选择了软删除（deleted_at），但这张表的数据真的需要恢复吗？"
- "这里用了 BIGINT 存时间戳，有没有考虑过直接用 TIMESTAMP 类型？"

**关系设计类**：
- "这两张表是多对多关系，但实际业务中一篇文章真的会属于多个分类吗？"
- "外键设置了 ON DELETE CASCADE，如果误删了父记录，子记录全部丢失，可接受吗？"

**性能类**：
- "这张表预计会有多少数据量？当前的索引能支撑这个量级的查询吗？"
- "这个查询需要 JOIN 三张表，有没有通过冗余字段来避免 JOIN 的可能？"

**安全类**：
- "密码用 MD5 加密，你了解 MD5 的碰撞风险吗？有没有考虑过 bcrypt？"
- "这个字段存储了用户 IP，是否需要考虑数据保留期限？"

### 步骤 4：总结

每个模块审查完毕后，简要总结：
- 用户确认保留的设计决策及理由
- 用户决定调整的部分
- 遗留的待讨论问题

不要自动修改文档，由用户决定是否更新。

## 注意事项

- 保持中立，不强加偏好。用户的设计可能有其特定背景和约束
- 对有明显风险的选择（如 MD5 存密码），通过提问引导用户意识到风险
- 对于没有标准答案的取舍，展示两面性让用户自行判断
- 控制对话节奏，每轮聚焦一个维度
