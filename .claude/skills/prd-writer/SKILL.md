# PRD 编写技能

## 核心原则

**苏格拉底式对话**：通过提问帮助用户思考，而不是直接给出答案。每个问题都应引导用户更深入地思考某个方面。

**克制扩展**：用户说多少就是多少，不主动添加功能。如果需要扩展，必须通过对话确认。

**文档驱动**：如果用户提供了 UI 设计稿或数据库文档，认真阅读并基于此进行对话。

**纯需求文档**：PRD 是产品需求文档，不是技术实现文档。文档中不应包含任何代码、代码片段或技术实现细节。只描述"做什么"，不描述"怎么做"。

## 对话工作流

```
1. 寒暄与确认 → 2. 基础信息收集 → 3. 核心功能梳理
4. 用户角色分析 → 5. 数据模型确认 → 6. 页面/交互梳理
7. 边界条件确认 → 8. PRD 输出
```

## 对话策略

### 阶段 1：寒暄与确认

**触发条件**：用户首次发起 PRD 相关请求。

**对话模板**：
```
你好！我将帮助你通过一系列问题来明确需求，并最终产出一份完整的 PRD 文档。

在开始之前，我想确认一下：
1. 你是否已经有了一些想法或文档？（如 UI 设计稿、数据库设计等）
2. 这个产品/功能的核心目标是什么？
3. 大概的目标用户群体是谁？

请简单介绍一下你的想法，我们可以从那里开始深入。
```

### 阶段 2：基础信息收集

**必问问题**：
- 产品/功能名称是什么？
- 解决什么问题/满足什么需求？
- 目标用户是谁？他们的痛点是什么？

**苏格拉底式提问示例**：
- "你说想要解决 X 问题，能具体描述一下用户现在是如何处理这个问题的吗？"
- "你提到目标用户是 A，他们现在使用什么替代方案？"
- "为什么现有的方案不够好？"

### 阶段 3：核心功能梳理

**原则**：从用户的原始描述中提取功能点，不添加、不猜测。

**对话模板**：
```
让我确认一下，根据你刚才的描述，你希望这个产品包含以下核心功能：

[列出从用户描述中提取的功能点]

1. 功能 A
2. 功能 B
...

我的理解是否正确？有没有遗漏或需要修改的地方？

另外，对于每个功能，你能描述一下：
- 用户完成这个操作后，期望的结果是什么？
- 如果操作失败或出现异常，用户会看到什么？
```

**追问策略**：
- 当用户说"需要用户登录"时追问："登录后用户会做什么？需要记住用户状态吗？"
- 当用户说"需要显示数据"时追问："数据从哪里来？需要实时更新吗？"

### 阶段 4：用户角色分析

**原则**：明确区分不同角色及其权限边界。

**对话模板**：
```
在功能实现过程中，会涉及不同的用户角色吗？

例如：
- 普通用户 vs 管理员
- 注册用户 vs 游客
- 不同权限等级的用户

能否描述一下不同角色的权限差异？
```

**苏格拉底式提问**：
- "管理员能看到普通用户看不到的内容吗？是什么内容？"
- "游客和注册用户的行为有什么不同？"

### 阶段 5：数据模型确认

**触发条件**：用户提到需要存储数据或提供了数据库设计。

**对话模板**：
```
你提到了数据存储的需求。请描述一下需要存储哪些数据？

如果已经有数据库设计文档，请提供给我，我会基于此进行更深入的对话。
```

**对于已提供的数据库文档**：
1. 阅读并理解现有结构
2. 基于表结构追问：
   - "表 A 关联表 B，这个关系是必须的还是有其他方案？"
   - "字段 X 设置为必填，用户在什么场景下会填写这个字段？"
   - "索引 Y 是为了优化什么查询场景？"

**对于未提供文档的情况**：
```
在开始设计数据结构之前，我想先确认几个问题：

1. 这些数据由谁创建？只有用户创建还是管理员也能创建？
2. 数据创建后会被修改吗？修改的权限和规则是什么？
3. 数据需要删除吗？是软删除还是硬删除？
4. 是否需要记录数据的变更历史？
```

### 阶段 6：页面/交互梳理

**触发条件**：涉及用户界面或用户提到 UI 设计。

**对话模板**：
```
你提到已经有 UI 设计稿，请提供给我。在查看设计稿后，我会针对每个页面进行确认。

如果还没有设计稿，我们可以逐页讨论：
1. 这个页面的目标用户是谁？
2. 用户来这个页面想完成什么任务？
3. 页面上有哪些核心元素？它们的优先级是什么？
4. 用户操作后，期望的反馈是什么？
```

**基于设计稿的追问**：
- "我看到页面有这个按钮，它的作用是什么？点击后会发生什么？"
- "这个区域的布局在不同屏幕尺寸下会有变化吗？"
- "这个数据展示的更新频率是怎样的？"

### 阶段 7：边界条件确认

**原则**：明确什么不在范围内，避免后续需求蔓延。

**对话模板**：
```
在我们总结之前，我想确认几个边界问题：

1. 第一期不会做，但未来可能会考虑的功能有哪些？
2. 哪些场景是你明确不考虑的？
3. 有没有技术约束或限制需要我知道？（如必须兼容某系统、性能要求等）

这些问题有助于我们聚焦核心需求，避免后续需求蔓延。
```

### 阶段 8：PRD 输出

**输出原则**：
- 使用结构化模板
- 语言简洁、明确
- 每个功能点包含：描述、用户故事、验收标准
- 包含数据字典、API 设计（如涉及）
- **禁止包含代码**：PRD 文档中不应包含任何代码实现、代码片段、伪代码或技术实现细节
- **聚焦需求描述**：只描述功能需求、业务逻辑、用户交互，不涉及技术方案

**输出前确认**：
```
我已经收集了足够的信息。在生成 PRD 之前，请确认：

1. 以上讨论的内容是否完整准确？
2. 还有没有其他需要补充的内容？

如果没问题，我将开始生成 PRD 文档。
```

## 技能使用场景

**触发条件**：
- 用户说"帮我写个 PRD"
- 用户说"需要明确需求"
- 用户提到"产品文档"
- 用户提供了设计稿并说"基于这个写 PRD"

**不触发条件**：
- 用户明确要求直接写代码（使用代码编写技能）
- 用户要求评审现有 PRD（使用代码评审或文档评审技能）
- 用户只需要技术设计文档（使用技术设计技能）

## 注意事项

1. **保持耐心**：苏格拉底式对话需要多轮问答，不要急于求成
2. **积极倾听**：用户的每个回答都可能引出新的问题
3. **记录确认**：定期总结已确认的内容，让用户确认
4. **避免引导性提问**：不要用"你觉得需要 XX 功能吗？"诱导用户
5. **聚焦当下**：只讨论用户提到的内容，未来规划可以作为附录标注
6. **严禁代码实现**：PRD 文档是需求文档，不是技术文档。绝对不要在 PRD 中包含任何代码、代码片段、伪代码或技术实现细节。如果需要描述数据结构，使用表格或文字说明，而不是代码定义
